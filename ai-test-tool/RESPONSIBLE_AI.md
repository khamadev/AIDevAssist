# Responsible AI in dev.ai

This document states, in one place, how dev.ai handles accessibility, fairness,
human oversight, and transparency. It exists so these commitments are checked
against actual behavior, not just described in a report.

## Human oversight

dev.ai can block a commit or push, but a human can always override that
block: set `AI_TEST_TOOL_OVERRIDE=1` before the git action. This is a
deliberate, visible escape hatch, not a silent bypass:

- Every override is printed to the terminal at the moment it happens.
- Every override is written to `.ai-test-tool/last_run_<stage>.json`
  (`human_override: true`).
- The documentation agent reads that file and adds the override to the
  commit's changelog entry, so it is on the record, not hidden.

dev.ai's verdicts are advisory by default and enforced only because a human
chose to wire them into git hooks. The override exists so that choice always
stays reversible on a per-commit basis, and so the tool never becomes an
authority nobody can question.

## Fairness and non-discrimination

Every check dev.ai performs is deterministic and code-based:

- The reliability agent classifies a test by whether it executes, whether it
  passes, whether its assertions can ever fail, and whether it references
  code that doesn't exist. None of these depend on who authored the change,
  their writing style, or anything outside the code itself.
- The compliance check (EU AI Act Article 50 disclosure) looks for a literal
  marker string in the file, applied identically to every contributor.

No agent scores a person. Every agent scores a change.

## Transparency and disclosure

- AI-generated test files must carry a disclosure marker
  (`# AI-generated by ai-test-tool`); the reliability agent fails the check
  if it's missing rather than assuming good faith.
- The documentation agent logs every commit's reasoning to `CHANGELOG.md`,
  including why a check failed and whether it was overridden, so the record
  survives independently of any one person's memory of what happened.

## Accessibility

- CLI and hook output is plain text: no color-only pass/fail signaling, no
  emoji, no icon-only indicators. A screen reader or a log file conveys the
  same information a sighted terminal user gets.
- Every failure prints its reason as text (`_print_failure_reason` in
  `cli.py`), not just a red exit code — a developer using a non-visual
  workflow gets the same explanation as one reading colored terminal output
  elsewhere.

## AI model interaction and data minimization

Test-maintenance sends function source code to Claude (via `ai_client.py`)
to generate tests — this is a real third-party data flow, not a
theoretical one, and is scoped deliberately narrow:

- Only the source of the specific untested function is sent, extracted via
  `ast.get_source_segment` — never the whole file, never the whole diff,
  never unrelated files in the repo.
- On every git-hook stage (`pre-commit`, `on-save`), only functions in
  files that actually changed are ever considered, capped at 5 per
  dispatch. Nothing is sent proactively or on a schedule from a hook.
- **The one deliberate exception:** running `ai-test-tool init` triggers a
  one-time, human-initiated full-repository scan (`test_maintenance.
  scan_repository`), capped at 25 functions, that considers every
  untested function in the repo, not just a current change — because a
  repo that hasn't had this tool running from the start needs a way to
  close existing gaps, not just prevent new ones. This only runs when a
  person explicitly runs `init` (or re-runs it without `--skip-scan`); it
  is never triggered by a commit, push, save, or any automated schedule.
- No git commit metadata (author name, email, timestamps), no other
  contributors' code, and no application runtime data (e.g. travel-planner
  user records) is ever included in a prompt.
- Before a function's source is sent to Claude, `secret_redaction.py` scans
  it for AWS access key IDs, PEM private key blocks, bearer tokens, and
  assignments to variables named like a secret (`api_key`, `password`,
  `token`, etc., including type-annotated assignments) and replaces the
  value with `[REDACTED]`. This runs unconditionally, inside the same
  process, before the prompt is built — not as an opt-in flag.
- Every redaction is visible, not silent: it's recorded per-function in
  `details.generated[].secrets_redacted`, and surfaced in the printed
  summary and the changelog entry the same way a human override is,
  because "a secret was in this code and was redacted" is exactly the kind
  of thing that shouldn't only be discoverable by re-reading the source
  after the fact.

Every other agent (hooks, reliability, documentation, notification)
operates entirely on the target repository's own files and git history and
sends nothing to any third party. Git commit metadata is written only to
the target repo's own `CHANGELOG.md` and local state files under
`.ai-test-tool/`.

## Not yet addressed

Stated plainly, rather than left implicit:

- Secret redaction is regex-based, matching known patterns and naming
  conventions (`secret_redaction.py`'s `_RULES`) — it has a real, expected
  blind spot: a credential that doesn't match any pattern (an unfamiliar
  naming convention, an unrecognized token format) passes through
  unredacted. It is a mitigation, not a guarantee.
- The model's output is trusted for test *content* (reliability.py verifies
  it by execution) but not audited for the prompt sent to it — there is no
  prompt-injection defense if a function's own source or docstring
  contained adversarial text aimed at the model.
